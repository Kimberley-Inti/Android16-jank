# 场景说明、Jank 分级与类型频次

本次更新只修改 Python 监测界面与采集后的展示统计，不修改 Android FrameTimeline 判定，无需重新编译或刷机。Windows EXE 未重打包，需运行更新后的 `main.py`。

## 场景标签

有可靠的场景 BEGIN/END 时，显示应用启动、应用切换、触摸拖动、抛滑请求等中文标签。
触摸拖动、抛滑仍标为推断，不能证明页面真的滚动。

没有匹配交互时：

- 尚无数据：等待场景数据。
- 无已知活动场景：暂无已识别交互。
- 已接回会话：提示历史交互未记录、等待新场景。
- 收到未匹配交互的帧：按其 layer/owner 显示最近的桌面、任务栏、系统界面或输入法图层上下文，明确标记推断。
- 归属证据也缺失：明确提示缺少场景证据。

原始 `primary_scene=UNKNOWN` 等字段保留，展示文本不会伪造设备没有报告的场景。

## BufferStuffing 是否计入

- `deadline_jank=0` 的单独 BufferStuffing 不计入 Deadline Jank，不进入 low/medium/high，也不进入其类型频次。
- 同一帧若同时出现 BufferStuffing 和 App/SF deadline miss，且设备报告 `deadline_jank=1`，仍统计这个 Deadline 帧。不能因为它也含 BufferStuffing 就删除实际 deadline miss。
- 原始辅助标签保留，可切换「辅助标签」或「全部标签」查看。辅助标签不等于没有性能问题。

## low / medium / high

这是项目的**呈现延迟展示分级**，不等同于 Android 原生 `severity`，不代表 CPU/GPU 根因，也不能直接等同于人的感知。只对设备已经确认 `deadline_jank=1` 的帧分级。

定义：

```text
T = 1 秒 / 当帧 refresh_rate
延迟 = actual_present_ns - expected_present_ns
ratio = 延迟 / T
```

若预期与实际呈现时间不可用，使用已有的 `delay_ns`；当两种值都存在时优先使用呈现时间差。

| 等级 | 条件 | 60 Hz 示例 | 120 Hz 示例 |
|---|---|---|---|
| low | 0 < ratio < 1 | 0 < 延迟 < 16.67 ms | 0 < 延迟 < 8.33 ms |
| medium | 1 ≤ ratio < 3 | 16.67 ≤ 延迟 < 50 ms | 8.33 ≤ 延迟 < 25 ms |
| high | ratio ≥ 3 | 延迟 ≥ 50 ms | 延迟 ≥ 25 ms |

缺有效刷新率、缺时间、延迟为零或负数时，保留 Deadline 事实，但程度归为「未分级」。未分级不强行塞进 low。
这里使用的是显示刷新周期，不是应用自身目标帧率的周期。

## Jank type 统计与比较

「Jank type 统计与比较」默认打开「low / medium / high 对比」：

- 三条颜色柱显示各等级事件数量，并单列未分级数量。
- 「Jank type 标签排名」并排显示 low、medium、high 三个独立榜单；每个榜单按本级数量降序排列，数量相同按类型名称稳定排序。
- 各榜只列该级实际出现的类型；计数变化后自动重新排名。
- 未分级另放独立页，不混入三个等级。
- 「原始组合排名」同样提供三个独立降序榜，保留完整 bitmask，例如 `72 = App deadline + BufferStuffing`。
- 每个榜单列出：排名、Jank type、数量、该级内占比、每分钟频次。
- 事件列表支持等级过滤，并显示 `low / 0.6T` 等分级依据。

计算方式：

```text
每分钟频次 = 本地收到的该级该类型次数 × 60 / 本地观察秒数
该级内占比 = 该级该类型次数 / 该级 Deadline 事件总数
```

观察时间包含没有事件的时段；接回会话从本地接回采集开始计算，不使用设备历史全会话时间。停止后频次冻结。
标志位可以重叠，次数与占比之和可能超过该级事件数和 100%；原始组合是互斥分布。
分级始终只统计本地收到的 Deadline 事件，不随「原始标签范围」切换而把辅助标签纳入。
顶部设备指标仍覆盖设备整个 session，可能大于本地分级数量之和。

## 导出

会话目录新增 `severity_summary.json`，包含分级阈值、方法版本、观察时长、各等级的组合/标志位次数、频次与占比。

`correlated_jank.jsonl` 新增：

- `jank_level`: low / medium / high / ungraded；辅助标签为 not_applicable。
- `severity_ratio`、`severity_lateness_ns`、`severity_period_ns`、`severity_method`。
- `scene_display`: 带证据说明的场景展示文本。

原始 `severity`、`deadline_jank`、`jank_type` 和原始日志不变。
`session.json` 新增 `severity_counts` 与 `severity_method`。
汇总文件每次周期 stats 和结束时更新，界面按本地数据实时显示。
导出中的组合/标志位各自按本级数量降序排列，新增 `rank` 字段，根对象的 `ranking_order` 说明排序规则。

## 为什么 medium 可能最多，low 可能最少？

分级按延迟阈值，不按分位数或固定比例分组。不存在 low 必须最多的要求。

- 统计对象已先被 Android 确认为 Deadline Jank，正常帧和单独 BufferStuffing 不在三个分级中。
- low 是不足 1 个显示周期的正呈现延迟；medium 覆盖 1 至不足 3 个周期，区间宽度也不同。
- 呈现与显示刷新节奏有关，一批帧集中晚 1～2 个周期时，medium 自然可能最多。这只是可能的解释，具体批次仍应检查原始时间与刷新率。
- high 的数量受当前场景、采样时长和多图层帧影响，不能据此推断 CPU/GPU 根因或判断系统整体性能正常。

本次复算最近已保存会话，逐条 `jank_level` 与代码按原始呈现时间、刷新率重新计算的结果一致，未发现错分。
阈值没有因用户希望的数量分布而改变，本次仅修改各等级的类型排名布局及导出顺序。

## 独立统计页面布局

窗口顶部提供「Deadline Jank / 监测与事件」与「Jank type 统计与比较」两个主标签。

- 监测页包含设备连接、开始/停止、当前应用/场景、设备累计指标、事件过滤与事件列表。
- 统计页独占窗口内容区，不再显示监测页的大块控制区和设备指标；顶部仅保留紧凑的会话状态、会话目录入口和返回监测按钮。
- 分级榜单随可用高度扩展。原始标签分布页提供自己的范围选择器，不需要先切回监测页操作。
- 切页不停止采集、不清空会话和计数；这是应用内整页布局，不会强制改变操作系统的全屏状态。

布局验证包含窗口映射检查、统计表可用高度比较和切页后计数保持；全部 22 项回归测试通过。
